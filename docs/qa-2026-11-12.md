Scope: https://pay-whop.onrender.com/, using the existing browser's synthetic sandbox customer and a newly completed one-time checkout. No live-money operations were performed.

| Check | Result |
| --- | --- |
| Checkout return / webhook | New payment appeared after refreshing; the return query alone did not create a charge or grant subscription access |
| Exact paid amount | Provider and Pay both recorded 599 USD minor units |
| Partial refund | The page requested USD 1.00; provider and Pay both reported exactly 100 minor units refunded |
| Saved methods | Refresh completed without an error and retained the member-scoped test card |
| Reconciliation | Completed without an error; the new payment remained a single row and its confirmed refund amount was preserved |
| Webhook backlog | Zero pending deliveries when checked after payment/refund |
| Invoice simulation | Reset → draft → issued → paid, with a new local activity history |
| Transfer simulation | Reset → pending → failed, with a new local activity history |
| Simulation isolation from billing | The payment table remained at six actual payment rows; simulation controls did not add a charge |
| Keyboard | Skip link and checkout-button navigation worked; focusable table regions and refund buttons were checked locally |
| Narrow layouts | Checked at 320px and 390px; no whole-page horizontal overflow. A billing readability issue was found and fixed |
| Regression suite | 100 tests / 369 assertions and Standard Ruby passed |

## Finding and correction

At 320px the tables technically fit the page, but IDs, dates, amounts and labels broke across many narrow lines. Billing tables now preserve readable columns in a locally scrollable region, with a visible small-screen hint and keyboard focus. The action column stacks buttons on mobile. Local browser checks confirmed that tabbing to refund controls scrolls them fully into view at 320px, with no page overflow; 390px was also checked.

The local UI check used a blocked-network preview with synthetic records. The deployed page was separately exercised against the actual sandbox before the layout correction, then rechecked after deployment.

## Limits of this pass

A fresh recurring checkout, new 3DS challenge, subscription pause/cancel/resume, real invoice issuance, internal transfer settlement and bank payout were not repeated in this pass. Existing evidence and provider limitations remain documented in [verification.md](verification.md). This is targeted QA, not a complete accessibility or production-readiness assessment.
